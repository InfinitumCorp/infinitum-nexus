# Labyrinth across Infinitum products

By **Infinitum Corporation®**. Repository changes only: no public website changes,
Vercel changes, deployment, production configuration or merges are part of this PR.

## Real Cumulus://ID authentication

`CidLabyrinth` uses the existing `CidService.authenticate()` opaque-token lookup,
not a decoded/unverified JWT, CID string, email, role header or requested org id.
The CID directory supplies the current org. Labyrinth supplies explicit org-wide
reader/writer/admin/owner roles; administrative operations additionally require
current CID directory admin status, and admin/owner assignments require a CID
org admin target. No unknown org is claimed automatically and no member is
silently promoted. Direct server `Labyrinth.forClient(cid, org)` remains only for
backward compatibility and is deprecated; production entry points do not use it.

Every retained handle reauthenticates on every operation. Session expiry,
revocation, org changes, team removal, CID consent revocation and plan revocation
are checked live. `LBRNTH` remains a paid client-org entitlement, not a free CID
feature. Every registered brand uses that same entitlement and repo scopes.

Browser clients sign in with the existing Cumulus passkey/MFA/social/SSO flow.
Nexus +SPCTR and Mail mount `POST /api/labyrinth` on their existing CID cookie.
A caller may alternatively supply an explicit CID bearer. Invalid bearer headers
never fall back to a cookie. JSON/custom-header requirements protect cookie calls
against CSRF; no permissive cross-origin CORS policy is added.

Explicit `consent` records the selected LBRNTH scopes on CID/Firmament but grants
neither a paid plan nor an organization role. It requires direct CID login, not a
delegated repository credential. It is not automatically called by save/load.

`token` exchanges the current logged-in CID session for a **15-minute repository-only
bearer**, useful to native/Worker/product clients. Only its SHA-256 hash, CID/org,
parent session id and expiry are held in server memory. It is not a general CID
session, cannot renew itself or grant consent, and stops working immediately
when its parent CID session is revoked, its org changes or its scope/plan is revoked.
The token cache is bounded (1000 total, 8 per parent session); restart invalidates it.
Never store these bearers in URLs, logs, localStorage or public app config. Keep them
in memory or a trusted server-side session. A future browser popup/PKCE handoff UI
is not supplied here; the authenticated API/SDK is the integration boundary.

## Runtime setup and transport

Local persistent +SPCTR/Mail startup accepts `LBRNTH_MASTER_KEY` (canonical base64,
32 bytes) and an operator-maintained `LBRNTH_ENTITLED_ORGS` allowlist. No values
are committed/generated by this change. HKDF-SHA256 derives a distinct client key
from the root secret, fixed LBRNTH domain salt and org id. The resulting encrypted
snapshot lives alongside each local server's private data. Without the key the
repository route returns **503**, never an in-memory/free fallback. Without an
org in the entitlement authority all repository operations fail closed. Hosts may
instead inject a trusted billing callback and durable storage via `CumulusConfig`.

Separate ODIN/EON/ARCHITECT/Mail servers use operator-configured `LBRNTH_ENDPOINT`
pointing to one authoritative Cumulus-backed `/api/labyrinth` service. Their thin
relays preserve the explicit CID/repository bearer and pin their own product id.
They do not reinterpret Access JWTs, shared product tokens, Better Auth ids,
preview users or email addresses as CID. Existing product API authorization stays
unchanged; EON's configured Cloudflare Access gate still runs before its relay.

The shared `@infinitum/lbrnth-client` package is browser/Worker-safe and has no CID,
crypto/key-store or filesystem dependency. Typed clients expose explicit
`repositories`, `createRepository`, `save`, `load`, `history` and `diff` calls;
central-session clients additionally expose `consent`, `provision` and `sessionToken`.
Save/load paths are server-namespaced under `products/<canonical-id>/`. CNDCTR and
ARCHITCT alias ARCHITECT; SCALUS aliases SCALVS. Existing head CAS and role/plan
checks remain authoritative. HTTP artifacts support UTF-8 text and explicit canonical base64 for binary bytes,
plus atomic multi-file commits. The shared `/labyrinth` UI supports text editing
and file import/download. See [workspace guide](LBRNTH-BUILD.md). HTTP bodies are capped at 2 MiB,
HTTPS is mandatory except loopback development, redirects are refused and outbound
requests have a 10-second timeout. Responses are no-store; tokens/claims are not
forwarded in cookies or Access/product-auth headers. No stored code is executed.

## Tests, safeguards and rollout limits

Tests exercise actual CID passkey-created sessions, directory membership,
expiry/revocation, scope/plan denial, admin demotion, explicit consent, delegated
credential expiry/non-renewal, all website registry entries, every implemented
Nexus SDK export, the real +SPCTR cookie route, VEIL anonymity and secure relays.
Standalone PRs include their own transport/runtime regression tests.

No universal identity federation between independently deployed CID stores is
invented. Point product relays at the authoritative CID deployment; do not assume
separate +SPCTR/Mail data directories share sessions. Existing CID directory/org
onboarding and trusted paid-plan provisioning must be completed before Labyrinth
is usable. Hosted/serverless +SPCTR remains disabled until a transactional durable
Labyrinth adapter is supplied—do not use local snapshot files on ephemeral Vercel
storage. All prior single-active-writer, capacity, archival, KMS/backup and
unanchored-audit limitations still apply. No firmware integration is claimed. The shared repository GUI includes explicit
scope consent and workspace provisioning; trusted CID organization onboarding
and the paid-plan authority remain host prerequisites.
